# llmposter v0.2.0 — Design Spec

## Purpose

Two goals: (1) production-ready CI/release pipeline so llmposter ships as a real tool, and (2) handler DRY refactor + failure simulation improvements from the v0.1.0 review backlog.

---

## Chunk A: CI/Release Infrastructure

### Pre-commit Hooks

`.pre-commit-config.yaml` with:
- `conventional-pre-commit` — enforce conventional commit messages
- `cargo fmt` — auto-format and re-stage on commit
- `cargo clippy` — deny warnings on commit
- `cargo check` — compilation check on commit
- `cargo test` — full test suite on push (pre-push stage)

### Auto-tag Workflow

`.github/workflows/auto-tag.yml`:
- Triggers after CI passes on main
- Reads version from `Cargo.toml`
- Creates `vX.Y.Z` git tag if it doesn't exist
- Uses `SKILLDO_RELEASE` org secret for push permissions

### Release Workflow

`.github/workflows/release.yml`:
- Triggers on `v*` tag push
- Cross-platform matrix builds:
  - `x86_64-unknown-linux-gnu` (ubuntu-latest)
  - `aarch64-unknown-linux-gnu` (ubuntu-24.04-arm)
  - `aarch64-apple-darwin` (macos-latest)
- Packages as `llmposter-{tag}-{arch}.tar.gz`
- Generates SHA256SUMS
- Uses `git-cliff` with `cliff.toml` for release notes from conventional commits
- Creates GitHub Release with artifacts

### Homebrew Tap

Release workflow includes a `homebrew` job that:
- Generates `llmposter.rb` formula from build artifacts + checksums
- Pushes to `SkillDoAI/homebrew-tap` repo under `Formula/llmposter.rb`
- Users install via `brew tap SkillDoAI/tap && brew install llmposter`

### cliff.toml

Standard git-cliff config for conventional commits, adapted from skilldo:
- Groups: Features, Bug Fixes, Documentation, Performance, Refactoring, Testing, CI/CD, Dependencies, Miscellaneous
- Skips release/chore(release) commits
- Links to GitHub compare URLs

## Chunk B: Code Quality

### Handler DRY Refactor (Trait-based)

**Problem:** All 4 handlers share ~100 lines of identical boilerplate. Every review fix had to be applied 4 times.

**Solution:** Define a `ProviderHandler` trait in `handler/mod.rs`:

```rust
pub trait ProviderHandler: Send + Sync {
    /// Which provider this handler serves
    fn provider(&self) -> Provider;

    /// Extract (model, user_message) from the raw JSON body
    fn extract_request_info(&self, body: &serde_json::Value) -> Result<(String, String), String>;

    /// Build a non-streaming text response
    fn build_response(&self, state: &AppState, model: &str, content: &str, prompt: &str, stop_reason: &str) -> String;

    /// Build a non-streaming tool-call response
    fn build_tool_call_response(&self, state: &AppState, model: &str, tool_calls: &[(&str, serde_json::Value)], prompt: &str) -> String;

    /// Build SSE frames for streaming text
    fn build_stream_frames(&self, state: &AppState, model: &str, content: &str, chunk_size: usize, prompt: &str, stop_reason: &str) -> Vec<String>;

    /// Build SSE frames for streaming tool calls
    fn build_tool_call_stream_frames(&self, state: &AppState, model: &str, tool_calls: &[(&str, serde_json::Value)], prompt: &str, stop_reason: &str) -> Vec<String>;

    /// Route path for logging
    fn route_label(&self) -> &str;
}
```

**Generic handler function** in `handler/mod.rs`:
```rust
pub async fn handle_request<H: ProviderHandler>(
    handler: &H,
    state: Arc<AppState>,
    body: String,
) -> Response<Body> {
    // 1. Parse JSON → 400
    // 2. Extract request info → 400
    // 3. Check streaming flag
    // 4. Match fixture → 404
    // 5. Verbose logging
    // 6. Error fixture → error status
    // 7. Response safety check → 500
    // 8. Failure simulation (latency, corrupt body)
    // 9. Streaming path: mpsc + spawn + truncation/disconnect
    // 10. Non-streaming path: text or tool-call response
}
```

Each provider file (`openai.rs`, `anthropic.rs`, `gemini.rs`, `responses.rs`) becomes:
- A struct implementing `ProviderHandler`
- An axum handler function that delegates to `handle_request`
- ~30 lines instead of ~200

**Gemini special case:** Gemini has path-based routing (`generateContent` vs `streamGenerateContent`) and JSON-array streaming. The trait handles this via:
- `extract_request_info` receives the full body + can inspect query params
- `build_stream_frames` returns frames; the generic handler decides SSE vs JSON-array based on a method `fn streaming_format(&self) -> StreamFormat` (SSE or JsonArray)

### Provider-Specific Error Shapes

**Problem:** All providers return OpenAI-style `{"error": {"message", "type", "code"}}`. Real Anthropic uses `{"type": "error", "error": {"type", "message"}}`.

**Solution:** Add a method to `ProviderHandler`:
```rust
fn build_error_response(&self, status: u16, message: &str) -> (StatusCode, String);
```

Each provider builds its own error shape. The generic handler calls this instead of `failure::build_error_body()`.

### `disconnect_after_ms` with `tokio::select!`

**Problem:** Current implementation uses `yield_now()` + elapsed check, which is unreliable at zero latency.

**Solution:** In the generic handler's streaming loop, use:
```rust
tokio::select! {
    _ = sleep(Duration::from_millis(disconnect_ms)) => {
        // Deadline hit — drop sender, stream ends
        return;
    }
    _ = async {
        // Normal frame-sending loop
        for frame in frames { ... }
    } => {}
}
```

This gives real deadline enforcement regardless of latency settings.

### `truncate_after_chunks` Semantics

**Problem:** Counts SSE frames (including preamble like ping, message_start), not content chunks. Same value means different things per provider.

**Solution:**
- Rename field to `truncate_after_frames` in YAML fixtures
- Keep `truncate_after_chunks` as a deprecated alias during v0.2.0
- Document clearly: "truncates the SSE stream after N frames, including preamble events"
- Count starts at frame 0

## Testing Strategy

- All existing 269 tests must continue to pass
- Handler refactor is a pure internal change — public API unchanged
- New tests for:
  - Provider-specific error shapes (Anthropic error format)
  - `disconnect_after_ms` with `tokio::select!` (deterministic deadline tests)
  - Trait-based handler produces identical output to old handlers (migration tests)
- Coverage target: maintain 98%+

---

## What's NOT in v0.2.0

- `cargo publish` to crates.io — separate step later
- Multimodal (image-only) request support
- Incremental tool-call argument streaming
- Windows builds (no demand yet)
